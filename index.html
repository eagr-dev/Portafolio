Password Manager API — Arquitectura Zero-Knowledge ● Desplegado en Nube
Sitio Web ↗ GitHub ↗
C# · .NET 10 Clean Architecture AES-256-GCM Redis MySQL xUnit Docker Oracle Cloud (OCI) Cloudflare
  • API REST donde el servidor nunca ve las credenciales en claro: el cifrado con AES-256-GCM ocurre en el cliente y la API solo almacena datos cifrados.
  • Sesiones efímeras y rotación de refresh tokens en Redis, con expiración automática por TTL.
  • Middleware de tarpit asíncrono que retrasa las respuestas ante intentos fallidos para frenar fuerza bruta, e idempotencia con UUIDs para descartar peticiones duplicadas.
  • Proyecto organizado en 4 capas (Clean Architecture), contenerizado y desplegado en Oracle Cloud detrás de Cloudflare.
  • Por qué zero-knowledge: el navegador cifra con AES-256-GCM antes de enviar y el servidor solo guarda datos cifrados. Si el usuario pierde su clave, ni yo puedo recuperarlos. Es cifrado reversible, no un hash.
  • Por qué Redis para sesiones: cada sesión nace con tiempo de vida, y puedo revocarla o comprobar si sigue activa al instante.
  • Por qué tarpit y no bloqueo de cuenta: retrasar las respuestas frena la fuerza bruta sin darle a un atacante la forma de dejar fuera a un usuario legítimo; bloquear cuentas sería abrirme un ataque de denegación de servicio.
Sistema de Reservas — Volta Vida (Spa) ✓ API completa
GitHub ↗
C# · .NET 10 Clean Architecture CQRS · MediatR xUnit EF Core MySQL Mercado Pago Twilio Docker
  • API para agendar citas y cobrar anticipos de un centro de bienestar, separando comandos y consultas con CQRS y MediatR.
  • Pruebas unitarias y de integración desarrolladas con xUnit para validar handlers CQRS, controladores de la API y lógica de negocio.
  • Prevención de reservas dobles concurrentes con bloqueo pesimista (FOR UPDATE) en MySQL.
  • Integración con Mercado Pago: webhooks procesados de forma idempotente para que un reintento no duplique el pago.
  • Confirmaciones por WhatsApp (Twilio) y correo SMTP. Solución en Docker, lista para un VPS en Oracle Cloud.
  • Por qué CQRS: el sistema es sobre todo lectura (el cliente consulta servicios y horarios antes de reservar), y separar consultas de comandos me permite optimizar cada lado por su cuenta.
  • Por qué FOR UPDATE: dentro de una transacción bloquea las filas consultadas. Si dos personas piden el mismo horario, la segunda espera; cuando entra, ya lo ve ocupado y sale sin reservar.
